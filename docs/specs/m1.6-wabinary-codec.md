# Atrocity M1.6 — WABinary Codec

## Verified reference observations

The current Baileys WABinary encoder uses:
- `LIST_EMPTY = 0`
- `DICTIONARY_0..3 = 236..239`
- `INTEROP_JID = 245`
- `FB_JID = 246`
- `AD_JID = 247`
- `LIST_8 = 248`
- `LIST_16 = 249`
- `JID_PAIR = 250`
- `HEX_8 = 251`
- `BINARY_8 = 252`
- `BINARY_20 = 253`
- `BINARY_32 = 254`
- `NIBBLE_8 = 255`
- `PACKED_MAX = 127`

Baileys writes node metadata as a list whose size is:
`1 + 2 * attributeCount + (contentPresent ? 1 : 0)`.
Small lists use `LIST_8`; larger lists use `LIST_16`.
Strings may resolve through a token map, packed nibble/hex form,
or raw UTF-8 with BINARY_8/20/32 length markers.

These behaviors are visible in the current reference encoder/decoder:
`encode.ts` writes list sizing, string tokenization/packing/raw strings,
attributes and node content; `decode.ts` reverses those representations.

## Atrocity implementation boundary

- `WABinaryCodec` owns framed node encode/decode.
- `ByteReader` / `ByteWriter` own primitive byte operations.
- `WABinaryProfile` owns token vocabulary/versioning.
- JID-special encodings and double-byte dictionaries are deferred to a
  versioned profile rather than silently guessed.

## Current limitation

This milestone is a verified **minimal subset**, not a claim of complete
WhatsApp wire compatibility. The production profile still needs:
- complete single-byte token vocabulary
- double-byte token dictionaries
- JID encodings
- exact compression/frame integration
- compatibility vectors against the target protocol
