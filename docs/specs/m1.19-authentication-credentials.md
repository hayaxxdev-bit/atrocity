# M1.19 — Authentication Credentials & Registration Bundle

## Scope

M1.19 introduces the durable credential domain and the shape needed to
construct `DevicePairingData`.

## Included

- `AuthenticationCredentials`
- `DeviceIdentity`
- `SignedPreKey`
- credential generator
- registration bundle abstraction
- conversion into ClientPayload `devicePairingData`

## Current reference

Current Baileys authentication state separates `creds` and `keys`, and its
registration flow derives registration-related fields, signed pre-key data,
identity-key data, and `DevicePairingData` before building a registration node.

References:
- https://github.com/WhiskeySockets/Baileys/blob/master/src/Utils/auth-utils.ts
- https://github.com/WhiskeySockets/Baileys/blob/master/src/Utils/validate-connection.ts

## Deliberate limitation

The current `CryptoProvider` exposes X25519 and SHA/HKDF/AES primitives but
does not yet expose Ed25519 signing. Therefore the generated signed-pre-key
signature in this milestone is a temporary deterministic placeholder derived
from a hash and MUST NOT be used as a production Signal signature.

Before any live registration is attempted, M1.20 must add audited signing
support and implement the actual Signal identity/pre-key construction.

## Security rule

Credential objects are durable secrets and must not be emitted through normal
runtime events or logs.
